- feat: reopen a fresh workspace with a warning when its restore point expired (#17269)
  > - **Detection:** `gitRestorePointExpired(recipe)` is true when the main restore point or any nested checkout's restore point has `expiredAt`.
  > - **Reopen** (`execution-workspaces.ts`):
  > - **Retention:** `markGitRestorePointExpired` now also marks nested checkouts' restore points, matched by object key.
- feat: expire idle open issues' worktrees with restore points (#17271)
  > - `isGitWorkspaceExpirationEligible(..., idleCutoff)`: in idle mode the closed-tree conditions are replaced by idle ones. No issue in the tree, and no other issue bound to the workspace, was updated after the cutoff, and no relevant run was created, started or finished after it. Runs of bound issues now count as relevant runs in both modes. Every other check stays, including no live run, recovery action, unsettled finalization, environment lease or running service.
  > - `gitWorkspaceLastActivityAt` returns the latest of those timestamps, sharing the same tree and run scope.
  > - `expireReconstructableGitWorkspace` takes `idleCutoff` and passes it to all three eligibility checks.
- feat: give nested managed checkouts their own restore points (#17257)
  > - **Allowed:** the checked-out branch's unpushed commits, plus its uncommitted, untracked and history-only work.
  > - **Still blocks:**
  > - **`COMMIT_EDITMSG`:** a nested checkout is a full clone, so its base git storage check now accepts a `COMMIT_EDITMSG` that matches a commit in its history, in strict and relaxed mode. It is read only if it is a regular file of at most 64 KB, opened without following symlinks and without blocking; anything else keeps the workspace (`unsupported_commit_message`). The main worktree's existing `COMMIT_EDITMSG` read uses the same bounded reader. A clean checkout with only an unpushed commit therefore reports `unpushed_managed_checkout`, which restore point mode can relax, instead of `unknown_base_git_files`.
- feat: expire closed git worktrees with unsaved work behind restore points (#17248)
  > - **When it applies:** with `PAPERCLIP_GIT_RESTORE_POINTS_ENABLED=true` (default `false`), a worktree that fails the reproducibility check for a relaxable reason is reconsidered once its issue tree has been closed for `PAPERCLIP_GIT_RESTORE_POINT_TERMINAL_DELAY_DAYS` (default `3`). The relaxable reasons are uncommitted or untracked files, a commit not on the remote, reflog or `ORIG_HEAD` history, and ignored `.env` files. A leftover `COMMIT_EDITMSG` still blocks expiration unless it matches a commit in the worktree's reflog, because restore points do not save draft messages.
  > - **What still blocks:** a relaxed inspection (`inspectGitCacheRecipeForRestorePoint`) keeps every other check. Nested managed checkouts, submodules, special git state, local config and other unique ignored files still prevent expiration.
  > - **Capture:** inside the existing source and lifecycle locks, a restore point is captured with the #17238 library against a remote-verified boundary (the `HEAD` itself, or its merge base with `origin/HEAD`), then encrypted, uploaded, read back and hash-checked (`git-restore-point-storage.ts`).
